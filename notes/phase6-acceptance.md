## 一、先解决的命名冲突

`contracts.py` 的 `TaskHandle.capability` **已经是 HMAC 租约令牌**（fencing token），不是"能力位"。计划里的"能力位"若同名，两个概念会共用一个词，且类型都是 `str`——混用不会报错。

裁定并落地：能力位一律叫 `skills`。这是本阶段最有价值的一条预防性决定，因为它拦下的是一类**不会在测试里出现、只会在生产写回时炸掉**的错误。

## 二、编制依据：双重证据，而不是一句注释

`staffing()` 不接受任何"任务数"参数，测试用两重证据钉住：

1. **签名检查**：`inspect.signature` 里不得出现 `queue_depth` / `pending` / `tasks` / `task_count` / `backlog` 等参数；
2. **行为检查**：往库里塞 1000 个待办任务前后，同样的 `active_by_pool` 得到**完全相同**的编制结果。

只有第 2 条不够——实现者可以偷偷查库；只有第 1 条也不够——参数名可以叫别的。两条合起来才排除了"编制受任务数影响"。

变异验证：给 `staffing` 加上 `queue_depth` 参数并按它截断 → 该测试立刻红。

## 四、对我自己决议的一处修正：`skills` 必须是三态

决议原文写 `skills: frozenset[str]`。实现时发现必须区分三种状态：

| 值 | 含义 |
|---|---|
| `None` | 该池**未声明**技能限制 —— 任何任务都能接 |
| `frozenset()` | 声明了，但零技能 —— **什么都接不了** |
| 非空集合 | 只能接被覆盖的任务 |

若把"未声明"也当成空集，**未配置技能的环境会变成"所有任务都不可调度"**——系统看起来在跑，实际一个任务都派不出去。若都当成 `None`，误配成空集的池会静默接走全部任务。

已修正决议文档并加注释说明原因。

## 五、两处设计判断

**编制下界是 0，不抛异常。** 资源满时返回空元组。抛异常会让"暂时没资源"看起来像"系统故障"，而那是正常路径。

**冲突默认 `REPORT`。** 两个子代理对同一事实给出不同答案，分歧本身就是最有价值的信息。`PRIORITY` 平手时也必须降级为 `REPORT`——不许用"后到覆盖"兜底，因为那意味着"谁在列表后面谁说了算"，而调用方完全看不出这个规则。

## 八、独立审查：三次尝试均因基础设施失败，改用差分测试

### 8.2 替代方法：差分测试 + 属性测试

既然换不了"人"，就换"技术"。变异测试只能证明"我写的断言能抓住我想到的错"；差分测试能证明"任意输入下实现是否与规格的字面翻译一致"。

做法：
1. **从决议文字独立写一份朴素参考实现**（`merge_ref` / `staffing_ref`），故意写得慢、直白、不做优化；
2. 用随机输入（固定种子）跑 3000 组 `merge` + 2000 组 `staffing`，逐字段比对；
3. 另外跑 2000 组 `staffing` 的**属性检查**：总位数 ≤ `max_running`、位名不重复、每池占用+新增 ≤ 配额、占用增加后编制不增加。

### 8.3 结果：1435 处不一致，两个真缺陷

首次运行 `merge` 差分报 **1435 处不一致**，`staffing` 差分与属性检查全部通过。

#### 缺陷一（BLOCKER）：预算短路了冲突检测

```
trial=10 parts=[{'a':'x','b':'x','d':'y'}, {'a':'y','b':1,'c':3}]
policy=FAIL  budget=max_bytes=0
impl = None（没抛）   ref = 抛 AggregationError
```

根因：预算检查与冲突检测在同一个循环里，**被预算丢弃的 key 永远进不了 `merged`，也就永远没机会与后续来源比较**。

后果分两层：
- 一般情况：`conflicts` 会随预算变化——调小预算，分歧凭空消失；
- 极端情况：预算紧到什么都进不去时，**`FAIL` 策略静默返回空结果**。调用方要求"有分歧就告诉我"，得到的既不是分歧也不是错误。

这违反 O5「绝不允许静默丢弃」，而且是最坏的形式：**静默成功**。

修法：拆成三遍——收集出现、判定（冲突与取值）、应用预算。`conflicts` 与 `dropped` 描述**输入**，`merged` 描述**输出**，三者互不影响。

#### 缺陷二（MAJOR）：`PRIORITY` 的冲突判定两个方向都错

| 场景 | 实现行为 | 应有行为 |
|---|---|---|
| 低优先级处有平手，但被严格更高优先级统一 | **误报冲突** | 结果无歧义，不报 |
| 最高优先级组内部就有两个不同值 | **漏报冲突** | 真正未决，必须报 |

根因：用"逐次比较 + 替换即裁决"的增量状态判断。替换那一刻只比较了优先级数值，看不到同组内还有别的值；而早先记下的平手又不会因为后来的统一而撤回。

修法：**不看过程，只看最终最高优先级组**——最高组内有几个不同值，就报几个。

#### 缺陷三（MAJOR）：`dropped` 按出现次数计而非按 key 计

同一 key 在三个来源里出现且都被丢弃时，`dropped` 报 3 而不是 1。数字虚高且随输入分布变化——它应该回答"丢了几个字段"，不是"跳过几次尝试"。
