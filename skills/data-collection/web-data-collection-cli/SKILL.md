# Web Data Collection with CLIs

## Output directory convention (user preference)

All Bazhuayu CLI collection output for this user MUST land under:

- WSL path: `~/bazhuayu_output`
- Windows path: `\\wsl.localhost\<distro>\home\<user>\bazhuayu_output` (UNC; type as `\\wsl.localhost\<distro>\home\<user>\bazhuayu_output` in Windows Explorer)

**Date-based archiving**: output files are grouped by collection day. Each day gets a top-level directory `<YYYY-MM-DD>/` containing `runs/` (per-run artifacts incl. `rows.jsonl`), `exports/`, `analysis/` (Excel/reports). Reusable task definitions stay in the top-level `tasks/`; helper scripts (`build_tasks.py`, `run_parallel.sh`, `run_batch.sh`, `analyze_weibo.py`) stay in the project root. Example: `2026-08-12/runs/parallel_20260812_204326/07_Deepfake/run_*/rows.jsonl`, report at `2026-08-12/analysis/微博_AI关键词_分析.xlsx`.

The project lives at `~/bazhuayu_output/` (Kali Linux WSL; was previously named `bazhuayu_ai_weibo` — do not recreate the old name). Scripts already derive the date dir themselves; run them from the project root and pass the batch dir explicitly to `analyze_weibo.py` (e.g. `python analyze_weibo.py 2026-08-12/runs/parallel_20260812_204326`). Do not hardcode the old directory name.

## Use when
Use for authorized public-web collection requests where a supported CLI can authenticate, create or reuse tasks, run browser-based collection, export results, and support analysis deliverables.

## Operating principles
- Separate **task creation**, **task configuration**, **collection**, and **analysis**. Do not call a task created until a task ID/file is returned and independently found/listed or validated.
- Prefer the CLI's machine-readable capability contract (`<cli> capabilities --json`) before selecting task-creation commands.
- Use direct, specific user requirements as the collection goal: source/site, search terms, per-term cap, time range, requested fields, and Excel/report outputs.
- **Clarify pagination scope in multi-keyword collection.** Interpret “抓取 50 页” as a batch-wide target unless the user explicitly says “每个关键词各 50 页”. State the interpretation before running; if it matters, ask once. For a batch-wide target, estimate rows from the site’s result-page size, allocate the cap across terms, and document the page estimate plus per-term allocation in batch metadata and the workbook methodology.
- Respect site terms, access controls, login, rate limits, and CAPTCHA. Do not attempt to defeat a CAPTCHA or bypass access controls; ask the user to complete any required login/verification in a visible browser.
- Never report imagined rows, task IDs, exports, or analyses. Verify each artifact by reading it, previewing data, or checking count/status output.

## Workflow

### 1. Preflight
1. Verify CLI executable and account authentication (`<cli> --help`, `<cli> auth status`).
2. Inspect machine capabilities (`<cli> capabilities --json`) and identify:
   - supported creation workflows;
   - browser/runtime mode and platform support;
   - available run/export commands;
   - whether actions have remote/cloud side effects.
3. Run the CLI diagnostic command (e.g. `doctor`) before launching a batch.
4. Determine whether the collection needs an authenticated site session. If required, arrange a supported visible browser/session workflow before starting bulk runs.

### 2. Select the right task path
- **Reusable template path:** search/view template metadata first. Use only if all required variables are exposed as actual template parameters.
- **URL-driven path:** use the CLI's agent/task-detection workflow for a provided entry/search URL when the template lacks variables or the user needs custom fields.
- **Existing-task copy path:** when `detect` is unavailable (e.g. SmartProxy missing linux-x64 native binding), copy an existing cloud task with `bazhuayu task copy <sourceTaskId> --json` and rename with `bazhuayu task rename <newTaskId> --name "新名称" --yes --json`. The copy inherits the full workflow (fields, XPaths, actions). This is a cloud-to-cloud operation — no browser needed.
- **Existing-task path:** inspect and validate an existing task before reuse; decode/export task definitions only as needed to confirm fixed inputs or fields.

For Bazhuayu specifically, agent task creation should follow `capabilities.machineContract.recipes.createTaskFromUrlWithAgent`: prepare context, visually review the detected page/candidate, preview an agent plan, apply it, validate, then run a small sample. Do not default to `detect --auto` when acting as an agent.

### 3. Validate before batch collection
1. **先跑验证再交付：** 创建或修改任务后，必须运行 `bazhuayu run <taskId> --max-rows 5` 并检查实际产出数据。不要仅凭任务创建成功就交付。关键检查：运行日志中是否有 `Loop.Error`（无匹配元素）、`Click.Error.NotFound`（元素找不到）、`Extract.Error`（提取失败）；`bazhuayu data history` 返回的 `rows` 是否 > 0；字段是否完整有效。
1. Confirm created task identity through a task list/show call; an HTTP/CLI `ok: true` with an empty result object is **not** proof that a remote task exists.
2. Validate the definition and inspect expected fields.
3. Run a small sample first (e.g. 5–20 rows per search term).
4. Inspect the sample `rows.jsonl` directly—not only the CLI summary. A `status: stopped` / `stopReason: max_rows` result means the runner saved rows, not that their extracted fields are meaningful.
5. Check representative fields: keyword/query, text/title, author/source, time, URL, and engagement where requested. Require non-empty primary content and all requested core fields in at least one representative row; compute per-field fill rates and reject the full batch when core fields are systematically blank.
6. Only after sample quality is acceptable run the requested collection cap.
7. Apply any user-specified display-name rule before the bulk run. If the user says that `*` is unacceptable, treat a masked nickname (for example `筱**`) as unusable: do not try to defeat platform masking, and exclude it from the final export. Since this can reduce yield substantially on Weibo, report raw count, masked-name rejections, and final accepted count separately.

### 4. Run and monitor
- Use explicit row caps per term; retain the term/query as a field so merged data remains traceable.
- Track task ID, run/lot ID, destination directory, row count, and errors for each term.
- Avoid unnecessary simultaneous browser runs; browser automation is resource-intensive and sites may throttle it.
- If a login/CAPTCHA interrupt occurs, pause and request user completion rather than silently retrying bulk runs.

### 5. Export and analyze
1. Export raw result data to a stable project directory in CSV/JSON and preserve the original output.
   - For a user-requested CSV-only delivery, create a UTF-8-with-BOM CSV. Include the source, all covered keywords (or a compact group label), final post-deduplication count, and collection date in the filename.
   - Normalize whitespace in textual fields and deduplicate by canonicalized detail URL (remove query strings). Independently verify the written CSV: row count, headers, core-field missing counts, and distinct canonical URL count must agree.
   - Treat `rows.jsonl` as an audit artifact but parse defensively: catch and count malformed JSON lines, omit only those malformed records, and report the omission count. Do not let one malformed line abort a usable batch export.
   - Put human-facing collection scope and quality explanation in a Markdown `README.md` / `collection_report.md` alongside the exports: sources and entry URLs, keyword coverage, raw/final counts, canonical-link deduplication, malformed-line omissions, field completeness, collection limits, blockers, and next actions. Keep CSV outputs record-only; do not use a CSV as a prose explanation or default quality-report sidecar.
   - When a user asks to remove duplicates, first create and verify the consolidated export and its Markdown report. Then remove only superseded **derived** CSVs whose contents are fully represented by that export; retain raw `rows.jsonl`, run metadata, task definitions, and logs for audit. Do not delete a distinct-source dataset merely because its keywords overlap.
2. Produce a derived Excel workbook, normally with:
   - `raw_data`: merged normalized rows with source keyword;
   - `summary_by_keyword`: count, date range, engagement summary;
   - `top_posts`: ranked posts using clearly documented metric/criteria;
   - `data_quality`: per-keyword results, missing-field rates, duplicates, and collection timestamps;
   - `methodology`: source, query terms, caps, collection time/timezone, limits, and caveats.
3. Verify the workbook exists, opens structurally, has expected sheets/row counts, and report its absolute path.

## CDP browser automation pitfalls

- **Chrome process management:** Using `pkill -f chrome` or `kill` inside a `terminal()` call can kill the Hermes terminal session itself (same process group → exit code -15). Never kill Chrome from a foreground terminal command. Instead: launch Chrome with `terminal(background=true, notify_on_complete=false)`, then kill it with `process(action='kill', session_id='...')`.
- **Python websockets vs Node.js ws for CDP:** The `websockets` library (v17+, package name `websockets`) frequently fails to connect to Chrome/Edge CDP with HTTP 500 (page-level WS) or 404 (browser-level WS). Use `websocket-client` (package name `websocket-client`, import as `websocket`) instead. If both Python libraries fail, Node.js with the `ws` module (built-in compatible, `npm install ws`) is the most reliable fallback — it connects to Chrome/Edge CDP without issues.
- **Scroll-container investigation:** When a page appears to have no scroll (docHeight ≈ windowHeight), check for **internal scrollable containers** before concluding the page doesn't scroll. Use `Array.from(document.querySelectorAll('*')).filter(el => { const s = window.getComputedStyle(el); return (s.overflowY === 'scroll' || s.overflowY === 'auto') && el.scrollHeight > el.clientHeight + 10 })` to find them. Xiaohongshu's search results live inside a `.feeds-page` div that scrolls independently of `document.body`. Scrolling it to the bottom still does NOT trigger more API calls on the web version — only ~20 results are ever loaded.
- **Cookie injection via CDP (user-provided cookies):** When a user provides cookies as JSON, the recommended approach is to inject them via CDP, but **Xiaohongshu's anti-bot system (`acw_tc` challenge) blocks this** — see `references/xiaohongshu-cdp-cookie-injection.md` for the complete workflow and limitations. Key technical notes: (1) Chrome 147+ removed `Storage.setCookie`/`Storage.getCookies`/`Storage.deleteCookies` (error -32601) — use `Network.setCookie`/`Network.getCookies`/`Network.deleteCookies` instead. (2) `Network.setCookie` returns `success: true` without actually persisting cookies when the anti-bot system is active. (3) `document.cookie` does NOT capture HttpOnly cookies — always use CDP `Network.getCookies` for the full set. (4) Add `--remote-allow-origins=*` flag for Chrome 147+ CDP connections. (5) Node.js `ws` module is more reliable than Python `websocket-client` for Chrome 147+ CDP.
- **API interception over DOM extraction:** When a SPA loads data via XHR/fetch, prefer `Network.enable` + `Network.getResponseBody` over DOM parsing. The API response is structured JSON with all fields (including engagement metrics the DOM may hide). See `references/xiaohongshu-cdp-card-fallback.md` for the full CDP interception pattern.

## Bazhuayu CLI notes
- The binary is `bazhuayu`; package naming may differ.
- `template search` and `template view` establish whether a template exposes user-configurable parameters. A template can have a search-input action hard-coded in its task definition while returning `parameters: []`; in that case `template-task update` cannot change that action.
- `template-task create` must be verified through `task list`/`task show`. Treat empty response data as unverified and do not claim creation.
- A browser-capable local run may require an X display/Xvfb on headless Linux. Diagnose platform/runtime prerequisites before running a batch, then re-run `doctor` after remediation.
- User-browser profile reuse is platform-dependent. Do not claim that a Windows browser login is automatically reusable from a WSL/Linux CLI.
- **Empty-run repair and card-stream fallback:** A generated task can validate yet complete with `total: 0` when the runtime cannot locate a dynamic result container (`Loop.Error`). Inspect `logs.jsonl` and `rows.jsonl`; never call that successful collection. Verify that the task has a `detection.session` reference so the runner injects saved cookies. If the native loop remains empty but the authenticated live browser DOM has result cards, preserve the Bazhuayu task/audit artifacts and use same-browser localhost-only CDP as a documented fallback: bounded scrolling, incremental JSONL writes, URL deduplication, and multiple consecutive no-new-record rounds before stop. Before every keyword transition, inspect the rendered page URL and login modal: a redirect to `/explore` plus QR/phone-login content is an authentication checkpoint, not an empty search result; pause and ask the user to reauthenticate in the still-open visible browser. State plainly that this is a browser-CDP fallback, not a successful Bazhuayu runner.
- **Search-filter evidence:** Treat a URL filter parameter such as `type=51` as filter-state evidence, not proof that every rendered card is pure 图文. Sample visible cards for playback/video markers and persist `内容类别`; when the user explicitly accepts all keyword-filtered cards, retain heterogeneous cards and document the scope expansion rather than silently discarding them.
- **Broadened Xiaohongshu scope:** If the user explicitly requests every keyword-filtered 图文/卡片 result regardless of canonical note/detail identity, retain heterogeneous search cards. Record `content_type`/`内容类别`, preserve the exposed card URL and its provenance, and label `帖子正文` as title/card-summary fallback. Search cards generally lack comments and favorites; leave those blank and disclose that only detail enrichment can fill them. Never relabel an author-profile URL as a note URL.
- **Local run timeout**: `bazhuayu run` default foreground timeout is 600000ms (10 min). Paged/scroll-heavy tasks (e.g. Weibo search >1 page) routinely exceed this and exit with `ENGINE_RUN_FAILED / Run timeout after 600000ms` — rows already saved in `rows.jsonl` remain valid. Pass `--timeout-ms` (e.g. 900000+) for deep-pagination batches.
- **`bazhuayu detect` saves to the cloud task list by default, not just locally:** All three modes (`--auto`, `--manual`, `--agent`) create a task in the **cloud task list** (visible via `bazhuayu task list` and in the Bazhuayu desktop client). The `--output` flag only controls where the local copy of the task definition is saved — the cloud task is always created regardless. Do NOT claim `detect` only produces a local file; that is a factual error. A cloud-save failure (`云端任务数量已达上限`) is the exception, not the rule.
- **SmartProxy detector linux-x64 limitation:** `@octopus/octopus-protect` only ships native `.node` binaries for darwin-arm64, darwin-x64, and win32-x64-msvc — no linux-x64. On Linux, `detect` fails with `Protected Smart requires a native binding for linux-x64`. The `doctor` suggestion to reinstall (npm bug 4828) will NOT fix this; the package simply lacks the target. Workarounds: (a) add `--legacy-detector` (but `--manual` then requires clicking a data group in the browser, not just Enter); (b) copy an existing cloud task with `bazhuayu task copy <taskId> --json` + rename to create a new cloud task without running `detect` at all.
- **Xiaohongshu search-card DOM field limitations:** Bazhuayu tasks can only extract DOM fields from search cards. Available: title, url, image, author, date, likes, summary. NOT available from DOM: comment_count, collected_count, share_count — these only exist in the SPA API response (`/api/sns/web/v2/search/notes`). To get them, use CDP `Network.getResponseBody` interception.
- **Cloud task limit (free plan 100 tasks):** When `detect` succeeds but cloud save fails with `"云端任务数量已达上限"`, the local task file is still written. Run it with `bazhuayu run <name> --task-file <path.json> [--max-rows N]`. The `--task-file` flag bypasses the cloud API entirely. See `references/bazhuayu-cli-validation.md` for details.
- **Parallelism is the real speed lever**: the per-row latency floor is the site's scroll/AJAX response (Weibo ~7.6s per scroll-batch regardless of task wait params; editing WaitSeconds/ScrollTime/AjaxTimeout only saved ~11%). To speed up a multi-keyword batch, run one `bazhuayu run` per keyword concurrently (shell `&` + `wait`, or a script); 3 parallel Weibo tasks on an 8-core/7GB box finished 3×100 rows in ~10min vs ~27min serial, no CAPTCHA. Mind the guidance in the skill not to over-subscribe browsers; 2-3 parallel instances is a sane ceiling for a laptop-class host.
- **Task XML is plaintext XAML**: the `xml` field of a local task `.json` is an uncompressed XAML workflow (not base64). Keywords live in `URL="..."` (NavigateAction), `TextToSet="..."` and `<InputText>...</InputText>` (EnterTextAction) — string-replace them to spawn keyword variants of a task.
- **Weibo (s.weibo.com) specifics**:
  - Anonymous `curl`/requests to `s.weibo.com/weibo?q=...` gets 302-redirected to `passport.weibo.com/visitor` (Sina Visitor System). A template task whose Navigate URL is `https://weibo.com/` (homepage) fails with empty rows on an unsigned-in browser because the homepage is a login wall (log shows `Click.Error.NotFound`).
  - Working pattern: set Navigate URL directly to `https://s.weibo.com/weibo?q=<urlencoded keyword>` and reuse a logged-in cookie set. The task XML often already embeds working `CustomizeCookie` entries (SUB/SCF/SUBP/ALF/XSRF-TOKEN/WBPSESS) — extract them (`&lt;CustomizeCookie&gt;...&lt;/CustomizeCookie&gt;` blocks) and verify with `curl -H "Cookie: ..."` against the search URL (HTTP 200 + `card-wrap` in HTML = login works).
  - Search-page relative XPaths (`//div[@class="content"]/...`, `//div[@class="card-act"]//li[1..3]`, paginator `//li[@class="cur"]/following-sibling::li/../../..//a[@class="next"]`) are stable across s.weibo.com; nickname comes back partially masked (e.g. `橘**`) by the platform.

## Scope expansion and content-type coverage

When a user says the initial result set is too small or explicitly broadens the scope (for example, from “answers only” to “all content returned by the keyword search”), treat that as an active workflow correction:

1. Stop or pause the narrow route when safe; do not keep spending time on a superseded route. Interpret wording such as “关键词输入框里出现的都采集” as including every relevant ordinary content card returned by that keyword search, not only the initially named subtype.
2. Preserve the first route's raw artifacts and provenance. Start a separate expansion run directory rather than overwriting the original JSONL.
3. Re-inspect the live result-card DOM/schema before writing the collector. Keyword search pages may contain answers, articles/columns, videos, ideas/pins, questions, and platform-generated AI result panels; include only authorized content types and exclude navigation, users, ads, and AI-generated summaries unless explicitly requested.
4. Use a stable content URL as the deduplication key. Normalize URL variants and retain `content_type`. If the requested CSV has legacy names such as `回答链接`/`回答正文`, map them to generic content URL/body semantics and document that mapping in the report rather than mislabeling records.
5. Keep the original keyword and expanded keyword(s) on every record. A record matching multiple keywords remains one global row with a multi-value keyword field; report per-keyword counts separately.
6. Sample every newly included content type before bulk collection. Verify that author, URL, date, engagement, and body/summary extraction are real DOM fields; do not count a page's “all sources” or AI answer panel as ordinary content records.
7. If detail-page extraction fails, preserve a clearly labeled search-card summary fallback and a `content_body_source`/quality note. Never present a summary as full text without disclosure.

See `references/zhihu-keyword-content-expansion.md` for the CDP result-card and multi-content extraction recipe. For scalable query intersections, URL merge rules, and exact-target delivery, see `references/zhihu-keyword-matrix.md`.

## Large-target collection and delivery discipline

When the user specifies a numerical total target (for example, 50,000 records) and says to keep finding additional sources if the current yield is insufficient:

1. Treat the target as **in progress**, not complete, until the final normalized count reaches it or each viable source path has a documented, evidence-based blocker.
2. Maintain a live gap calculation: `target - final global deduplicated rows`. Do not label a partial export as the completed dataset merely because one batch finished.
3. Expand in this order: remaining handbook keywords on already validated sources; additional validated result pages/sections on those sources; then new accessible sources. Sample and validate core fields before every new bulk route.
4. If a browser run ends at a smaller count than its requested cap, inspect `rows.jsonl`, result JSON, and stop reason. Preserve saved rows, but record the shortfall and continue with another bounded batch rather than treating the cap as achieved.
5. Keep raw per-run artifacts under `runs/`; publish one current, globally deduplicated primary CSV in `exports/`. Remove superseded/intermediate CSV exports only after the replacement CSV is verified. Put methodology, source coverage, per-keyword counts, de-duplication, quality figures, and access blockers in a companion Markdown file rather than auxiliary CSV reports when the user requests MD-first documentation.
6. When the user supplied a collection handbook, append an execution-record section with actual counts, artifact paths, tested blockers, and the remaining gap. Never overwrite the original strategy without preserving it.

## Browser-gated search and manual verification
- Treat a detector result such as `DETECT_PAGE_BLOCKED` / `security_challenge` as an access-state checkpoint, not evidence that the target has no data. Preserve the exact URL, title/snippet, and detector diagnostics.
- For a site whose homepage and search page both trigger a security challenge, do not repeatedly retry the same `detect --manual <search-url>` command. First establish that the manual browser has a usable interactive display/stream, then launch a minimal homepage session with `--manual --save-session --session-name <name>` so the user can complete login/verification before task detection.
- Browser-runtime readiness does not prove a usable interactive session. Verify that a browser window is reachable; if the manual process exits before user interaction with stream/display errors, stop retrying the identical route and report the prerequisite failure. Use a supported native browser environment or another supported visible-session setup rather than claiming a session was saved.
- **Do not ask the user to log in until a window is actually on a visible desktop.** `bazhuayu doctor` can report Chrome ready via Xvfb while `DISPLAY` is empty; `detect --manual` then exits with `Missing X server or $DISPLAY`. Check `echo $DISPLAY` and `/tmp/.X11-unix` first. On this host the working path is Win-KeX / TigerVNC (`DISPLAY=:1`) plus a persistent independent Chrome `--user-data-dir`, then cookie/session handoff — not a pasted `--manual` command with no display.
- After user verification, independently confirm the saved session/task artifact and rerun a bounded sample. Never infer authentication or collection success from a launched process alone.
- In WSL/Linux, distinguish the independent temporary browser from a Windows Chrome profile: a login performed in Windows is not automatically available to the WSL browser unless a documented supported browser/session integration is active. `bazhuayu browser use user` is unsupported on Linux.
- **Xiaohongshu:** marketplace `template search 小红书` can return zero templates. After a verified login, build from a search URL or clone a local task JSON and swap the keyword. Schema, display check, and parallel-run notes: `references/xiaohongshu-collection.md`. **Key findings:** (a) search returns only ~20 results per page but pagination IS possible via Vue 3 Pinia store actions (`searchNotes({page: N})`) — see `references/xiaohongshu-collection.md` section "Pagination via Pinia store actions"; (b) API interception via CDP `Network.getResponseBody` yields full `interact_info` (likes, comments, favorites, shares) that DOM extraction misses; (c) detail pages are blocked even with valid cookies — body content is unavailable; (d) CDP card fallback documented in `references/xiaohongshu-cdp-card-fallback.md`; (e) cookie injection via CDP is **blocked by the `acw_tc` anti-bot challenge** — see `references/xiaohongshu-cdp-cookie-injection.md` for full details. See also `scripts/xhs-pinia-pagination.js` for a reusable paginated collection script.
- **`--manual` detect unreliability via terminal tools:** `bazhuayu detect --manual` opens a Chrome window and waits for user Enter. When run through an agent terminal tool, the command is easily interrupted (exit code 130/SIGINT). Each retry opens a fresh Chrome without saved session, so the login wall reappears. Do not retry endlessly. If `--manual` keeps failing, create a local task file manually with `detection.session` referencing an existing cookie session. See `references/xiaohongshu-linux-session-task-creation.md` section "Manual task file creation fallback" for the workflow.
- **`bazhuayu task list` shows only cloud-saved tasks, not local files:** A local task `.json` created manually or via `detect` with `--task-file` is NOT visible in `bazhuayu task list`. The list command queries the cloud API, not the local filesystem. When the user asks why a task doesn't appear in the list, explain this distinction. The task can still be run with `bazhuayu run <taskId> --task-file <path.json>`. To save a task to the cloud, use `detect` (auto/manual/agent) or `template-task create` -- but both require interactive user input for login-gated sites on Linux.
- **`--manual` Enter key via pipe trick:** `bazhuayu detect --manual` waits for the user to press Enter after each step. The Enter key CAN be sent programmatically via `(sleep N && echo) | bazhuayu detect ... --manual`. Each `echo` sends one Enter. Typical timing: first Enter at 25s (login confirmation), second at 30s (data region), third at 35s (pagination). This works on Linux with a visible display (VNC/Xvfb). The `--manual` mode is not fully interactive-free — the user may still need to log in and click a data group in the browser for `--legacy-detector` — but the pipe trick eliminates the need for manual terminal interaction.
- **`--manual` background process stdin limitation:** When `bazhuayu detect --manual` is run as a background process (via `terminal(background=true, notify_on_complete=true)`), the process's stdin is not available — `process(action='submit', session_id='...', data='')` fails with `Process stdin not available (non-local backend or stdin closed)`. This means the Enter-key pipe trick (`(sleep N && echo) | bazhuayu detect ... --manual`) is the only way to programmatically advance the `--manual` flow from a background process. Use a single foreground `terminal()` call with the pipe trick rather than a background process, or use VNC + a foreground `terminal()` call with the pipe trick.
- **VNC remote assist for `--manual` mode in headless WSL:** When `bazhuayu detect --manual` is run in a headless WSL environment with Xvfb (`DISPLAY=:1`), the browser opens in the virtual display — invisible to the user. To let the user see and interact with the browser, start a VNC server that shares the Xvfb display, then run `detect` as a background process:

  ```bash
  # Terminal 1: Start VNC server sharing Xvfb :1
  x0vncserver -display :1 -passwordfile /dev/null -rfbport 5901 &
  # Windows VNC client connects to localhost:5901

  # Terminal 2: Run detect --manual (user sees browser via VNC)
  bazhuayu detect "<URL>" --manual --save-session \
    --session-name "<name>" --output task.json --json
  ```

  **Hermes Agent workflow:** The agent starts `x0vncserver` as a background process, then starts `bazhuayu detect --manual` with the pipe trick in a **foreground** `terminal()` call (since background processes don't support stdin). The agent tells the user to connect via VNC (Windows VNC client → `localhost:5901`). After the user logs in, the pipe sends Enter at the appropriate times.

  **Limitations:** Requires a VNC client on Windows and WSL network access. The pipe trick sends Enter at fixed intervals — the user must complete the login within the first wait period. If the login takes longer, adjust the `sleep` values. The `--manual` mode needs 3 Enter presses (login confirmation, data region, pagination).\n- **Cloud task step naming convention:** When creating or modifying Bazhuayu tasks, use Chinese names for all workflow steps. Each step name should clearly describe its function. See `bazhuayu-auto-collection` skill for the full naming convention table.\n- **Cloud task XOML update via API (last resort):** When `bazhuayu detect` cannot create a task (SmartProxy broken on Linux), you can modify a cloud task's XOML by calling the `saveTaskInfo` API directly. This requires: (a) get the cloud task's XOML via `GET /api/task/getTask?taskId=...`; (b) modify the XML locally; (c) re-encode with `encodeTaskXml`: `Buffer.from(xml, 'ucs2') → gzipSync → 4-byte LE length prefix → base64`; (d) POST to `/api/task/saveTaskInfo` with the updated `xoml` field. ## Zhihu authenticated-browser fallback
- When Zhihu's home/search page is classified as a security challenge, do not repeatedly retry `detect --manual`: the detector can run page-access checks before its manual wait and exit before the user can scan.
- First establish a usable visible WSL display/browser session and let the user complete login. If Bazhuayu's independent detector cannot reuse the custom signed-in profile, keep the signed-in profile running with a localhost-only Chrome DevTools Protocol port, export only same-site Zhihu cookies, and write a Bazhuayu cookies-only session under `~/.octopus/browser-sessions/`. Verify both the session file and an authenticated result page; never infer login success from a launched process.
- A template `create` response with an empty `data` object is not proof of a remote task. Re-query `task list` with the template ID and proceed only when a concrete task ID is returned and inspectable. Templates with `parameters: []` cannot substitute the user's keywords; use a supported URL/agent path or a validated local fallback instead of mutating a fixed template.
- For Zhihu search results, validate repeated `.ContentItem.AnswerItem` cards and `a[href*="/question/"][href*="/answer/"]` links. Search cards can provide author, date, likes, and comments, but the full answer body requires opening the rendered answer detail page and extracting the answer rich-text container. Validate several detail pages before bulk collection.
- Keep the source keyword on every row and deduplicate globally by canonical answer URL, because an answer can match multiple keywords. Preserve raw rows and a collection report even when the available result set is far below the requested target.
- If the user asks to continue after exact-term yield is low, do not repeat only those same terms. Create a separately logged expansion batch of semantically adjacent queries (term variants, synonyms, common incident wording, and governance/mitigation phrasing).
